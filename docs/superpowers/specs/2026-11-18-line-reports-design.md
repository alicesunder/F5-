# รายงานจาก LINE + แก้ระบบเข้าสู่ระบบ (ระยะที่ 1: หน้าเว็บ)

## เป้าหมาย
เจ้าหน้าที่ส่งรายงานในกลุ่ม LINE แล้วบอทนำรายงานเข้าเว็บ ฝอ 5 และจัดเข้าแผนกให้อัตโนมัติ
ผู้บังคับบัญชาจะเห็นรายงานทั้งหมดในที่เดียว ส่วนแต่ละแผนกจะเห็นเฉพาะรายงานของตัวเอง

ระยะที่ 1 (เอกสารนี้) ทำเฉพาะหน้าเว็บโดยใช้ข้อมูลตัวอย่าง
ระยะที่ 2 ค่อยต่อฐานข้อมูลกลาง (Supabase) กับ webhook ของบอท LINE

## แนวทางที่พิจารณา
- **A. กล่องกลาง + เมนูย่อยในแต่ละแผนก (เลือกแบบนี้):** มีภาพรวมสำหรับผู้บังคับบัญชา ส่วนแต่ละแผนกยังทำงานอยู่ในหน้าของตัวเองได้ ใช้ข้อมูลชุดเดียวกัน
- B. มีเฉพาะในแต่ละแผนก: ไม่มีภาพรวม หัวหน้าต้องกดเข้าไปดูทีละ 4 ที่
- C. มีเฉพาะกล่องกลาง: คนในแผนกต้องออกจากหน้าของตัวเองมาหารายงาน

## การออกแบบ
- เมนูหลักใหม่ `line-reports` ชื่อ "รายงานจาก LINE" อยู่ใต้ "ศูนย์งานด่วน" ในแถบด้านข้าง
- เมนูย่อย "รายงานจาก LINE" ในทั้ง 4 สายงาน ใช้คอมโพเนนต์เดียวกันโดยล็อกตัวกรองไว้ที่แผนกนั้น
- ข้อมูลแต่ละรายงานประกอบด้วย: เวลา, กลุ่ม, ผู้ส่ง, หน่วย, ข้อความ, รูป, แผนก (`admin` | `relations` | `disaster` | `volunteer` | `unassigned`), คำสำคัญที่ใช้จัดแผนก, สถานะ (`new` → `acknowledged` → `in_progress` → `done`), บันทึกการดำเนินการ
- การจัดแผนก: ถ้ากลุ่มนั้นผูกไว้กับแผนกใดแผนกหนึ่ง ใช้แผนกนั้น ถ้าไม่ได้ผูก ให้ดูคำสำคัญใน 150 ตัวอักษรแรก (ใช้กติกาเดียวกับ `line-to-discord-worker-v4.js`) ถ้าไม่เข้าเงื่อนไขไหนเลย ให้เป็น "ยังไม่จัดหมวด" และให้คนกด "ย้ายแผนก" เองได้
- `lineReportService` ใช้แบบเดียวกับ `bppReportService` (subscribe + localStorage) เพื่อให้ระยะที่ 2 สลับไปใช้ Supabase ได้โดยไม่ต้องแก้ UI
- ข้อมูลตัวอย่างทุกชิ้นมีป้าย "ข้อมูลตัวอย่าง" กำกับ
- ดีไซน์ใช้สีม่วงเดิมของเว็บและสีประจำแผนกจาก `DEPARTMENT_COLORS` ใช้สีเขียว LINE เฉพาะที่ป้าย

## ระบบเข้าสู่ระบบ
- เอาอีเมลและรหัสผ่านที่ใส่ไว้ล่วงหน้าออก และเลิกแสดงชื่อเจ้าหน้าที่บนหน้าแรก
- ตรวจรหัสผ่านโดยเทียบค่า SHA-256 กับ `VITE_FO5_ADMIN_PASSWORD_SHA256` ไม่เก็บรหัสผ่านไว้ในโค้ด
- ยกเลิกการพาเข้าระบบเป็นผู้ใช้คนแรกเมื่อหาผู้ใช้ไม่เจอ และให้สลับบทบาทได้เฉพาะคนที่เข้าระบบแล้ว
- ข้อจำกัด: ตราบใดที่ยังไม่มี backend การตรวจนี้ยังทำในเบราว์เซอร์ ระบบจะปลอดภัยจริงเมื่อย้ายไปใช้ Supabase Auth ในระยะที่ 2

## สิ่งที่ไม่ทำในระยะนี้
- webhook ของบอท LINE และฐานข้อมูลกลาง
- การส่งข้อความตอบกลับเข้ากลุ่ม LINE

# ระยะที่ 2: ฐานข้อมูลกลาง (Supabase) + บอท LINE

## แนวทางที่เลือก (ผู้ใช้เลือกแนวทาง A)
- **A. ต่อยอดบอทเดิม (เลือก):** Cloudflare Worker เดิมยังเป็นผู้รับ webhook ของ LINE และส่งเข้า Discord ต่อ แต่เพิ่มการบันทึกลง Supabase พร้อมกัน ไม่ต้องตั้งค่า LINE ใหม่
- B. ย้ายไป Supabase Edge Function ทั้งหมด: เหลือที่เดียว แต่ต้องตั้ง webhook ใหม่และเลิกส่งเข้า Discord จึงเสี่ยงกว่า
- C. สร้างบอทใหม่: ไม่ได้อะไรเพิ่ม

## สิ่งที่ตัดสินใจโดยผู้ช่วย (ผู้ใช้ยังไม่ได้ยืนยันรายข้อ)
- โปรเจกต์ Supabase ใหม่ชื่อ `fo5-command-center` ภูมิภาคสิงคโปร์ ค่าใช้จ่าย $0 อยู่ในบัญชีแพ็กเกจฟรีที่เชื่อมไว้แล้ว
- ข้อสงสัยที่เป็นของผู้ใช้และยังไม่ได้ตอบ: (1) บอท v4 ใช้งานจริงอยู่ใน Cloudflare หรือไม่ (2) มีกี่กลุ่ม LINE และผูกกับแผนกอย่างไร (3) ข้อมูลรายงานของหน่วยจะเก็บในบัญชี Supabase ส่วนตัวแบบฟรีได้หรือไม่ ระบบรองรับทั้งกลุ่มรวมและกลุ่มแยกแผนก จึงไม่บล็อกการสร้าง แต่ข้อ (3) ต้องให้ผู้ใช้ยืนยันก่อนใช้ข้อมูลจริง

## เป้าหมาย / ไม่ใช่เป้าหมาย
- เป้าหมาย: ข้อความจากกลุ่ม LINE ถึงหน้าเว็บภายในไม่กี่วินาที รองรับรูปภาพ แสดงสดโดยไม่ต้องรีเฟรช เฉพาะผู้ล็อกอินอ่านได้ ปิดข้อจำกัดความปลอดภัยของระยะที่ 1
- ไม่ใช่เป้าหมาย: ให้บอทตอบในกลุ่ม, หน้าจอจัดการการผูกกลุ่มกับแผนก (ใช้ SQL ไปก่อน), ระบบหลายผู้ใช้และสิทธิ์รายคน, ย้ายข้อมูลเก่าจาก Discord
- สิ่งที่ล้มเหลวแม้ทำงานได้: ข้อความหายเงียบๆ, รายงานรั่วถึงคนที่ไม่ได้ล็อกอิน, บอทเดิมที่ใช้งานอยู่พังระหว่างพัฒนา

## การออกแบบ
**ฐานข้อมูล (ตารางใน schema `public`, เปิด RLS ทุกตาราง)**
- `line_groups(group_id pk, name, dept null, created_at)` ผูกกลุ่มกับแผนก ถ้า `dept` ว่างให้จัดตามคำสำคัญ
- `line_reports(id uuid pk, line_message_id unique, group_id, group_name, sender_user_id, sender_name, unit, message_type, text, media_paths text[], dept, matched_keyword, status, note, received_at, created_at, updated_at)` ค่า `dept` และ `status` มี check constraint ตรงกับชนิดฝั่งเว็บ `unique(line_message_id)` กันซ้ำเมื่อ LINE ส่งซ้ำ
- ที่เก็บไฟล์แบบส่วนตัว `line-media` เก็บรูปที่บอทดึงจาก LINE
- สิทธิ์: ผู้ล็อกอิน (`authenticated`) อ่านทุกแถว และแก้ได้เฉพาะคอลัมน์ `status`, `note`, `dept` (ผ่าน trigger หรือ column privileges) การเพิ่มแถวทำโดยบอทด้วยคีย์ `service_role` เท่านั้น ผู้ใช้ไม่ล็อกอิน (`anon`) ไม่มีสิทธิ์ใดๆ
- เปิด Realtime ให้ `line_reports`

**บอท (Cloudflare Worker v5)** ไฟล์ใหม่ `line-to-discord-worker-v5.js` ในโฟลเดอร์โปรเจกต์ ไม่แตะ v4
- ขั้นตอนเดิมทั้งหมดคงไว้ (ตรวจลายเซ็น, ชื่อผู้ส่ง, ส่ง Discord)
- เพิ่ม: จัดแผนก (ผูกกลุ่มก่อน แล้วค่อยคำสำคัญ ใช้ชุดคำเดียวกับ `LINE_ROUTES` ฝั่งเว็บ), ดึง "หน่วย" จากข้อความด้วย regex รูปแบบ `กก.ตชด.<เลข>` / `บก.ตชด.ภาค <เลข>` ถ้าไม่พบให้ว่าง, อัปโหลดรูปไป Storage, บันทึกลง `line_reports` ผ่าน Supabase REST ด้วย `Prefer: resolution=ignore-duplicates`
- ความล้มเหลวของ Supabase ต้องไม่ทำให้ส่ง Discord ล้ม และกลับกัน (สองทางแยกกัน ใช้ `Promise.allSettled`) แล้ว log ข้อผิดพลาด
- ตัวแปรลับเพิ่ม: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (ผู้ใช้ตั้งใน Cloudflare เอง)
- เก็บเฉพาะข้อความจากกลุ่ม (เหมือน v4) และเคารพ `ALLOWED_GROUP_ID`

**เว็บ**
- เพิ่ม `@supabase/supabase-js` และ `src/lib/supabase.ts`; ตัวแปรสาธารณะ `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (ปลอดภัยเพราะ RLS)
- `lineReportService` เขียนใหม่ให้อ่านจาก Supabase + Realtime โดยรักษารูปแบบ `subscribe/getAll/setStatus/moveToDept/setNote` เพื่อให้ `LineReportsView` แก้น้อยที่สุด (ต้องรองรับสถานะโหลด/ผิดพลาด) รูปภาพแสดงผ่าน signed URL อายุสั้น ลบข้อมูลตัวอย่างและปุ่มรีเซ็ตเมื่อเชื่อมต่อสำเร็จ
- เข้าสู่ระบบด้วย Supabase Auth (`signInWithPassword`) แทนการเทียบแฮช ลบตัวแปร `VITE_FO5_ADMIN_PASSWORD_SHA256` และโค้ดที่เกี่ยวข้อง session จัดการโดย supabase-js
- สร้างผู้ใช้ `chairot.s@royalthaipolice.go.th` แล้วปิดการสมัครสมาชิกเอง (disable signups) ผู้ใช้ตั้งรหัสผ่านใหม่เอง

## ลำดับการส่งมอบ (ปลอดภัยต่อของที่ใช้งานอยู่)
1. สร้างโปรเจกต์ + schema + RLS + bucket (ตรวจด้วยตัวตรวจความปลอดภัยของ Supabase)
2. เขียนและทดสอบ worker v5 กับข้อมูลจำลองโดยยังไม่ deploy
3. เว็บอ่านจาก Supabase และ Auth (ทดสอบในเครื่อง)
4. ผู้ใช้ deploy worker v5 และตั้งความลับ แล้วทดสอบด้วยข้อความจริงในกลุ่มทดสอบ
5. ค่อยสลับเว็บจริงบน Vercel

## ที่เหลือให้ผู้สร้างตัดสินใจ
รายละเอียด SQL/ชื่อคอลัมน์, รูปแบบ regex ของหน่วย, วิธีสร้างผู้ใช้ Auth รายแรก, การจัดการรูปที่เกินขนาด
